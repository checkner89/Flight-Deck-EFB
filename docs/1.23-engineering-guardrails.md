# Flight Deck EFB 1.23 Engineering Guardrails

Flight Deck EFB 1.23 extends the stable 1.22.1 baseline. Existing working pilot flows are compatibility contracts, not rewrite targets.

## Compatibility first

- Preserve existing Taxi, Flight Tracking, Archive, Briefing, Ground Services, SimConnect and updater behavior unless a story explicitly changes it.
- Prefer additive domain services and adapters over renderer-wide rewrites.
- Keep persisted flight records backward compatible. New fields must remain optional when older records are loaded.
- Any lifecycle, recorder, state-engine or route change requires a focused regression test.

## Single state pipeline

- SimConnect telemetry is ingested once and distributed through the existing state engine.
- Flight Journey, Operational Assistant and readiness logic consume normalized state instead of starting independent polling loops.
- Provider integrations such as SimBrief, SayIntentions, BeyondATC and GSX remain adapters. Provider-specific payloads must not leak into general UI logic.

## Performance budget

- Do not add unbounded `setInterval` or recursive timers in feature modules.
- Coalesce high-frequency telemetry updates before persistence and expensive rendering.
- Keep flight history and map rendering bounded through sampling, slicing or viewport-aware rendering.
- Avoid repeated full-array calculations on every telemetry tick when incremental state is sufficient.
- Lazy-load or defer secondary information that is not needed for the current operational context.
- Expensive derived data must be cached against stable input signatures where practical.

## UX and reliability

- Operational state changes must be explainable: source, severity, context and recommended action where relevant.
- Missing integrations degrade gracefully and must not block unrelated pilot workflows.
- Automatic actions must provide a manual correction path.
- A second desktop launch must focus the existing instance and must never create a second server, SimConnect session, tray or main window.

## Release discipline

- Do not rewrite an already published release tag.
- Materialization and release scripts must stay reproducible from a clean checkout.
- Before merging 1.23 work, run syntax checks plus the existing release/operations regression suite and any new focused tests.
