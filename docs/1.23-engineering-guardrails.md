# Flight Deck EFB 1.23 Engineering Guardrails

## Compatibility first

- Existing working 1.22.1 behavior is the baseline. New 1.23 capabilities must be additive unless a replacement is explicitly validated.
- Flight Recorder, Taxi, Ground Safety, Briefing, Archive, SimConnect and updater behavior keep regression coverage while 1.23 evolves.
- New state models should adapt existing services rather than duplicate telemetry polling or persistence.

## Performance

- Prefer one normalized telemetry/state pipeline over module-specific polling loops.
- Cache derived flight state and recompute only when relevant inputs change.
- Avoid unbounded arrays for telemetry, alerts, messages or map points; use sampling/retention limits appropriate to the feature.
- Keep network integrations independently throttled and fault-tolerant so one unavailable provider cannot stall the EFB.
- Lazy-load non-current modules and heavy document/map work where practical.

## Lifecycle

- Exactly one Flight Deck EFB application instance may own the local server, SimConnect session and tray lifecycle.
- Secondary Windows launches must terminate before importing the main application lifecycle and must focus the existing instance.
- Window close continues to hide to tray so second-screen hosting remains available; explicit Quit performs server/tray cleanup.

## Code quality

- Centralize shared domain concepts such as flight phase, readiness, operational alerts and planned/actual route state.
- Keep provider adapters separate from domain logic.
- Prefer small pure functions for state derivation and explicit lifecycle ownership for timers, sockets and subscriptions.
- Add regression tests with every change to startup, recorder completion, flight-state transitions or persistence.
